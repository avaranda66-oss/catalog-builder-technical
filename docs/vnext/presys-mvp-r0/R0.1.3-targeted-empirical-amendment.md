STATUS: APPROVED TARGETED AMENDMENT FOR FOUNDATION-PROOF-01 CONTINUATION
DATE: 2026-09-09
SUPERSEDES: exactly two R0.1.2 height decisions described below

## Why this amendment exists

FOUNDATION-PROOF-01 reproduced two empirical counterexamples against R0.1.2. They do not invalidate the VNext direction or the remaining frozen contracts. They reopen only rowspan AUTO/MIN height allocation and browser-derived table-height overflow comparison.

### A. R0.1.2 rowspan allocation was practically non-minimal

The reproduced overlapping-span case has base row heights `[100000,100000,100000] U` and two span requirements of `407789 U`. The R0.1.2 sequential equal-deficit distribution produced `[203895,255842,151947] U`, total `611684 U`. A feasible witness `[100000,307789,100000] U`, total `507789 U`, satisfies both constraints inside the authored `550000 U` frame. Artificial expansion was `103895 U` (`10.3895 mm`, about `20.46%`) and caused a false practical `TABLE_CONTENT_OVERFLOW`.

R0.1.3 replaces only that allocation rule.

## Rowspan minimum-total-extra solver

For each row `i`, compute the base height before rowspan constraints:

- `FIXED_MM`: exact authored height; it never grows.
- `AUTO`: intrinsic height.
- `MIN_MM`: `max(intrinsicHeightU, minHeightU)`.

Let growable rows (`AUTO`/`MIN_MM`) be indexed in semantic row order as `g0..g(m-1)`. Let `x[k] >= 0` be derived extra height for growable row `gk`. For each rowspan interval, compute once from base heights:

`deficitU = max(0, requiredSpanContentHeightU - sum(baseHeightU of every row in the span))`.

The growable rows touched by one rowspan form a contiguous interval `[l,r]` in the growable-row sequence. If `deficitU > 0` and the span contains no growable row, emit `ROW_CONTENT_OVERFLOW / ERROR`. Otherwise impose:

`sum(x[l..r]) >= deficitU`.

Define prefix extras `P[0]=0` and `P[k+1]=P[k]+x[k]`. The constraints become forward lower-bound edges:

- non-negative extra: `P[k+1] >= P[k]` with weight `0`;
- rowspan `[l,r]`: `P[r+1] >= P[l] + deficitU`.

All edges go forward in semantic growable-row order, so they form a DAG. R0.1.3 computes each `P[k]` as the maximum incoming predecessor value plus edge weight, equivalently the longest-path value from `P[0]`. Then `x[k]=P[k+1]-P[k]` and each derived row height is `baseHeightU + x[k]` for growable rows or exactly `baseHeightU` for fixed rows.

This assignment is canonical and minimum-total-extra. Any feasible prefix vector must satisfy every forward edge and therefore must be at least the longest-path value at every prefix; in particular its final prefix `P[m]`, which equals total extra height, cannot be smaller. The longest-path assignment attains that lower bound. All inputs and edge weights are integer `PhysicalLengthU`, no division or floating point is used, so all outputs remain integer U. Equal constraints are resolved by the same maximum value; input/DOM constraint order cannot alter the result. The componentwise-minimum prefix vector is the deterministic secondary canonicalization when several row vectors share the same minimum total.

For the reproduced counterexample, the canonical R0.1.3 result is `[100000,307789,100000] U`, total `507789 U`, so the authored `550000 U` frame no longer overflows.

### B. R0.1.2 table-height comparison crossed the Q/U quantization boundary incorrectly

The reproduced Chromium boundary case measured `renderedIntrinsicHeightQ = 4838` and `projectedAuthoredFrameHeightQ = 4838` for authored `frame.heightU = 200000`. R0.1.2 converted the browser measurement back to U, yielding `qToU(4838) = 200008 U`, and incorrectly emitted `TABLE_CONTENT_OVERFLOW`.

R0.1.3 compares the final browser-rendered table envelope in the same renderer projection space:

```text
renderedIntrinsicHeightQ <= uToQ(authoredFrameHeightU)  -> OK
renderedIntrinsicHeightQ >  uToQ(authoredFrameHeightU)  -> TABLE_CONTENT_OVERFLOW / ERROR
```

Equality in Q is therefore never converted into a false domain inequality. `PhysicalLengthU` remains the authority for authored and persisted geometry. `PhysicalPixelQ` remains renderer-only and is never persisted or written back into the document. `qToU` remains valid for diagnostics and for algorithms that genuinely need to consume a Chromium measurement in the domain row-height solver, but it is not the authority for the final table-envelope-vs-frame comparison after both sides have already been quantized into Q.
